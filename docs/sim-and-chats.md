# Номера SIM, переписка и выбор всех записей

В списке СМС кнопка «Новая СМС» открывает выбор SIM и получателя, затем чат. В карточке входящей СМС известная SIM и получатель выбраны и заблокированы. Если принимающая SIM неизвестна или больше не подключена, пользователь выбирает номер отправителя вручную из доступных SIM. Получатель остаётся фиксированным; сервер проверяет его по карточке. Ручной выбор используется только для ответа и не меняет сохранённые сведения о входящей СМС. История показывает переписку выбранной пары номеров и исходное сообщение карточки. Номера +7/8 нормализуются. Ответ на текстовое имя отправителя недоступен.

«Выбрать все» отмечает все сохранённые записи данного типа на всех страницах, включая скрытые поиском. Выбор сохраняется при смене страницы и сортировки. Удаление подтверждается с полным количеством выбранных записей; сервер удаляет только перечисленные идентификаторы, поэтому новые события, пришедшие после выбора, сохраняются.

Поиск в списке СМС проверяет номер отправителя и полный текст сообщения, в списке звонков — номер и текст транскрибации обоих каналов. Поиск подстроки не зависит от регистра, в том числе для кириллицы, и выполняется по всей истории до разбиения на страницы. В телефонных запросах допускаются пробелы, скобки и дефисы; в тексте цифры и знаки ищутся буквально. Пустой запрос снимает фильтр, отсутствующий текст возвращает пустой список.

В списке звонков кнопка «Голосовой вызов» открывает форму с номером отправителя. Доступные SIM сообщает рабочий бот. При выполнении задания он повторно проверяет соответствие номера и порта, чтобы смена SIM не привела к вызову с другого номера.

## Настройка маршрутов

`SMS_SIM_PORTS_JSON` задаёт соответствие порта и телефонного номера для входящих СМС. Для голоса дополнительно указываются реальные маршруты шлюза:

```dotenv
VOICE_CALLS_ROUTES_JSON=[{"port":1,"number":"+79990000001","endpoint":"gsm-port1","prefix":""},{"port":2,"number":"+79990000002","endpoint":"gsm-port2","prefix":""}]
CALL_GSM_INBOUND_DIDS_JSON={"1001":1,"1002":2}
```

Номера условные. Endpoint должен существовать в Asterisk и вести на нужную SIM. Если используется один endpoint, можно задать разные префиксы, которые шлюз удаляет при маршрутизации в соответствующий GSM-порт. Простое переименование endpoint не выбирает SIM. До настройки второго маршрута следует публиковать только проверенный маршрут.

Входящие вызовы нужно различать по DID, передаваемому шлюзом, либо `sim_port=N` в CDR userfield. Один общий endpoint для обоих GSM-портов не даёт достоверной информации о принимающей SIM. Исторические записи дополняются только при наличии подтверждения; отсутствующие сведения не угадываются.

Без `VOICE_CALLS_ROUTES_JSON` используется прежний endpoint и номер `TG_DEFAULT_SIM`, если он задан в `SMS_SIM_PORTS_JSON`. Telegram-команда без выбора SIM использует первый опубликованный маршрут. При изменении порядка маршрутов учитывайте этот вариант.

## Диагностика распознавания

В новых звонках отдельно сохраняется состояние обоих каналов: `recognized`, `no_speech` или `unrecognized`. Последнее означает, что VAD выделил звуковой фрагмент, но распознаватель не выдал текст; это не доказательство наличия разборчивой речи. Карточка показывает пояснение для такого канала. Сам звук, VAD и модели распознавания не меняются.

`event_metadata_maintenance.php` требует API-аутентификацию. Он позволяет дополнить только `local_number`, `sim_port` и `transcription_channels`. Обновления сверяют SHA-256 всей исходной записи под тем же файловым lock, что добавление/удаление; перед изменением создаётся закрытая резервная копия. Текст, аудио и удалённые записи не восстанавливаются и не заменяются этим API.
