# Оптимизация Python-службы

Приложение остаётся на Python. Вычисления GigaAM/faster-whisper и конвертация FFmpeg используют прежние модели, параметры и нативные библиотеки.

## HTTP и очереди

Все обращения к PHP-хостингу используют общий `httpx.AsyncClient` на время работы службы: до 8 соединений, до 4 свободных соединений, keep-alive 30 секунд. Для разных операций сохранены прежние таймауты. Telegram-прокси не меняет маршрут этих соединений; хостинг доступен напрямую. Отдельные экземпляры API-клиентов создают свой пул лениво и предоставляют `aclose()`; переданный извне клиент закрывает его владелец.

Автоматического повтора HTTP POST нет. Потерянный ответ на `claim` не должен создавать повторный SMS/вызов; существующие токены захвата, журналы и повтор только сохранения результата остаются прежними. При остановке службы работники завершаются до закрытия общего пула.

Heartbeat сообщает `has_pending` для СМС и `has_due` для голосовых заданий. При пустой очереди бот не делает второй запрос `claim` и не запускает Asterisk CLI. Результаты уже выполнявшихся заданий сохраняются даже при пустой очереди. Перед захватом готового голосового задания по-прежнему проверяется занятость Asterisk. Наличие задания — только подсказка; окончательный захват остаётся атомарным на хостинге.

Пауза между проверками уменьшена с 3 до 2 секунд. В ожидании это примерно 2 запроса за цикл вместо 4. Поле активности работника записывается раз в 15 секунд; изменение SIM/подключения шлюза применяется сразу. Срок определения недоступного работника остаётся 90 секунд. Обновление PHP нужно загрузить **до перезапуска бота**: `sms_outbox_store.php` и `voice_outbox_store.php`. Старый бот совместим с новым хостингом; новый бот при отсутствии подсказок использует прежний порядок heartbeat/claim.

## Память и аудио

NumPy, faster-whisper, ONNX и ReportLab не загружаются при обычном запуске бота. ASR-зависимости загружаются при первой транскрибации, PDF — при первой непустой расшифровке. Уже загруженная модель остаётся в памяти для быстрых последующих вызовов: это сокращение начальной памяти, а не обещание малого RSS во время/после ASR.

WAV отправляется на хостинг через открытый файл без предварительного `read()` всей записи в память. После FFmpeg проверка тишины читает PCM блоками по 8192 отсчёта и останавливается на первом отсчёте с амплитудой не меньше прежнего порога. Тишина проверяется полностью, включая звук в самом конце; границы длительности и размера не менялись.

Зависимости и модели не удаляются; переключение на faster-whisper остаётся доступным. Объём пользовательских записей не меняется. Меньше становятся лишние выделения памяти, TLS-рукопожатия, запуск процессов Asterisk CLI и записи heartbeat на хостинге.

## Проверка

```sh
python -m unittest discover -s tests -p 'test_*.py'
php tests/sms_outbox_test.php
php tests/voice_outbox_test.php
```

Тесты включают реальное переиспользование TCP-соединения и переподключение после закрытия сервером, отсутствие повтора неоднозначного POST, потоковую передачу аудио, обработку результатов при пустых очередях, приоритет обычных звонков, порог тишины, отсутствие раннего импорта ASR/PDF и сохранность атомарного захвата заданий.

На Pi следует сравнивать одинаковые состояния: отдельно свежий бот без загруженной модели, отдельно процесс после одинаковых записей ASR. Падение RSS после перезапуска прогретого бота само по себе не доказывает экономию памяти. Контроль распознавания — по хешу всей `conversation`, включая слова, каналы и временные метки; контроль FFmpeg — по SHA-256 WAV.
